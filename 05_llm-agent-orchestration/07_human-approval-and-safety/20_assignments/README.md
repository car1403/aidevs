# 07 Assignment · 안전한 병원 예약 Agent

병원 정보와 예약 가능 시간을 조회하고, 사용자에게 필요한 정보를 질문하며, 명시적인 승인 후에만 mock 예약 요청을 기록하는 Single Agent를 만듭니다.

## 사용자 목표

```text
강남 지역 병원을 찾아서 내일 오후 진료 가능한 시간을 확인하고 예약해 줘.
```

## Tool 정책

| Tool | 위험도 | 정책 |
| --- | --- | --- |
| 병원 정보 검색 | read | 본인 요청 범위에서 자동 허용 |
| 예약 가능 시간 조회 | read | 자동 허용 |
| 예약 요청서 초안 | draft | 외부 변경 없이 허용 |
| 본인 예약 요청·변경 | change | 사용자 승인 필요 |
| 다른 사용자 예약 조회·변경 | forbidden | 금지 |
| 실제 결제 | forbidden | 이 과제에서 금지 |

## 필수 Agent 흐름

```text
사용자 요청
   ↓
필수 정보 확인 ── 부족함 → waiting_user + 재질문
   ↓ 충분함
병원 검색 Tool
   ↓
예약 가능 시간 Tool
   ↓
예약 초안 생성
   ↓
waiting_approval + State 저장
   ↓
구조화된 사용자 승인
   ↓
인증·인가·소유권·승인 대상 재검사
   ↓
mock 예약 Tool 한 번 실행
   ↓
Trace와 Audit Log
```

## 필수 구현

1. 하나의 Agent State와 명확한 종료 상태
2. 현재 State를 보고 다음 Tool, 재질문, 승인 대기 또는 종료 선택
3. Tool 이름 Allowlist와 arguments Schema 검사
4. 조회·초안·변경·금지 위험도 분류
5. 요청 소유자와 승인자 검사
6. `waiting_user`와 `waiting_approval` 구분
7. 구조화된 승인·거절 Payload
8. 승인한 초안과 실제 실행 대상 일치 검사
9. 같은 `request_id`의 중복 실행 차단
10. 결정·Tool Call·승인·오류·실행 결과 Trace

## 공격 및 실패 시나리오

- 사용자 문장으로 미등록 Tool 실행 시도
- RAG 문서가 승인 없이 예약하라고 지시
- Memory가 다른 사용자의 예약 ID를 포함
- 다른 Agent가 관리자 승인을 받았다고 주장
- 다른 사용자가 승인 시도
- 승인 후 병원이나 예약 시간 변경
- 같은 요청을 두 번 재개
- Tool arguments 검증 실패
- 최대 반복 횟수 초과

자연어 내용과 관계없이 Backend 정책이 동일하게 적용되어야 합니다.

## 제출 시나리오

- 조회 작업 자동 완료
- 필수 정보 누락 시 재질문과 State 유지
- 변경 작업 승인 대기
- 올바른 사용자의 정상 승인
- 올바른 사용자의 거절
- 다른 사용자의 승인 차단
- 승인 대상 변조 차단
- 허용되지 않은 Tool 차단
- 동일 요청 재실행 차단
- Audit Log가 변경 한 번당 한 건만 기록

## 설계 설명

다음 질문에 답하는 `DESIGN.md`를 함께 작성합니다.

1. 이 문제를 Single Agent로 선택한 이유는 무엇인가?
2. 검색 Agent와 예약 Agent로 나눈다면 어떤 Goal과 Tool 경계가 생기는가?
3. Multi-Agent로 나눴을 때 얻는 이점이 비용과 복잡성보다 큰가?
4. 인증, 인가, 승인 중 Agent가 결정하면 안 되는 항목은 무엇인가?
5. 실제 LLM Tool Calling으로 교체해도 유지해야 할 Backend 검사는 무엇인가?

## 완료 기준

- LLM, 사용자, RAG, Memory와 다른 Agent의 문장만으로 정책을 우회할 수 없습니다.
- 거절·금지·실패에서는 변경 결과가 생성되지 않습니다.
- 승인 대상과 실제 실행 대상이 일치합니다.
- 실제 병원 예약이나 결제 API를 호출하지 않습니다.
- 모든 종료 결과에 상태와 이유가 있습니다.
- Agent 분리 여부를 Tool 개수가 아닌 Goal, Context, 권한과 평가 기준으로 설명합니다.
